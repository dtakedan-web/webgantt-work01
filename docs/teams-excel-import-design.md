## 1. 目的・概要

Teams（SharePoint/OneDrive）で共有されている週間予定表Excel（`予定表(サンプン).xlsm`と同一フォーマット）から、メンバーごとの予定を読み取り、WebGanttのタスクとしてインポートする機能を追加する。

**本機能の最大の特徴（Google/Outlookカレンダー連携との違い）**: WebGantt本体（`gantt-collab.html`）やサーバー（PHP API）だけでは完結せず、**ユーザーのブラウザにインストールする新規コンポーネント「ブラウザ拡張機能（Edge/Chrome、Manifest V3）」が必須**となる。これは、Excelファイルの取得に必要な認証（SharePointのブラウザCookie認証）が、WebGanttサーバー側からは技術的に到達不可能な社内ネットワーク内の認証情報であるため。

**対象範囲（本フェーズ）**: Teams OneDriveで共有された`.xlsm`形式の週間予定表のみ。取得範囲は1週間単位で最大4週分。

**本改訂版での主な変更点（2026-08-18）**:
- タスク反映方式を**方式Q（サーバー直接送信方式）に確定**（旧版で暫定採用していた方式Pは不採用。4.2節参照）
- 認証を**新規トークン発行機能**で実装することを確定（4.1節参照）
- 拡張機能ポップアップに「送信先プロジェクト選択」と合わせて「取り込む予定のチェックボックス選択」UIを追加（新規要望1、6節・8節参照）
- Excelセル内の改行区切りテキストを複数タスクに分割する仕様を追加（新規要望2、9節参照）
- 同一名称タスクが日をまたぐ場合の連続タスク結合ロジックを追加（新規要望3、9節参照）
- 本機能のサーバー側コードを既存コードから明確に分離し、将来の削除を容易にする方針を明記（新設11節）

## 2. 方式検討の経緯（重要・必読）

### 2.1 断念した方式

| 案 | 内容 | 結果 |
|---|---|---|
| 案X | 本番サーバー（`/media/HDD1_DATA/Web/WebGantt/`）から社内LAN経由でExcelにアクセス | **不採用**（サーバー設置環境の制約により社内LANへの経路が無い） |
| 案Y | ユーザーが手動でExcelファイルをアップロード | **ユーザー却下**（「外部連携と趣旨が変わる」、都度手動DL＋アップロードの手間を避けたい） |
| 案Z | Microsoft Graph API + Azure AD OAuth（`Files.Read`スコープ） | **断念確定**。`REDACTED-EMAIL`実機テストで「管理者の承認が必要」ブロック画面を確認。Task B（Googleカレンダー連携時のGraph API検討）・Task C（Outlookカレンダー連携時の`Calendars.Read`検討）と全く同じ`risk-based step-up consent`の壁（`docs/office-calendar-import-design.md` 2.1節参照） |
| 案（VBAマクロ拡張／ローカルエージェント／メール送信／Power Automate） | 第1ラウンドで提示した4案 | ユーザーが全て懸念を表明し不採用 |
| **方式P（タブ連携方式）** | 拡張機能のContent Scriptで、開いているガントチャートタブに`gantt:op`イベントを発火させる方式 | **不採用確定（2026-08-18）**。ユーザーより「タブでプロジェクトを開いておく必要があり、使い勝手が悪い」との判断（4.2節参照） |

### 2.2 採用方式: SharePoint REST API（Cookie認証）+ ブラウザ拡張機能 + サーバー直接送信（方式Q）

ユーザーから示された重要な制約「**ガントチャートを操作するPCと、会社アカウント(`REDACTED-EMAIL`)を使うPCが同一**」を前提に、以下を実機検証した：

1. ブラウザの開発者コンソールから `fetch(location.origin + "/sites/msteams_b3d137/_api/web/currentuser", {credentials:'include'})` → **`status: 200`**
2. SharePointの`shares` API（`https://suzumond.sharepoint.com/_api/v2.0/shares/{base64エンコードされた共有URL}/driveItem`）を叩き、`@content.downloadUrl`（署名付きダウンロードURL）を取得 → **`status: 200`**
3. 取得した`downloadUrl`から実際にファイルをfetchし、`blob.size`（510,811バイト）・`blob.type`（`application/vnd.ms-excel.sheet.macroenabled.12`）を確認 → **成功**

**結論**: Azure AD OAuth・Graph API・アプリ登録・管理者同意のいずれも一切経由せず、**ブラウザの既存Cookie認証だけでExcelファイルの完全なバイナリを取得できる**ことが実証された。この仕組みをコード化して自動実行するには「ブラウザの中で動作するプログラム」が必要であり、それが実現できるのが**ブラウザ拡張機能**である。

拡張機能が取得・解析したデータの反映方式は、当初「方式P（タブ連携）」を推奨提案したが、ユーザーの使い勝手優先の判断により**方式Q（拡張機能からWebGanttサーバーへ直接HTTPS POSTし、サーバー側でタスクを追加する方式）に確定**した（4.2節）。

### 2.3 拡張機能の配布・運用方針

- 社内ITポリシー確認の結果、`edge://policy`で`ExtensionInstallForcelist`/`ExtensionSettings`が既にAD経由で運用中であることが判明
- ユーザー方針: **「情報システム部門への確認は難しい。IT部門を回避した形で進めるしかない」**（明言・確定）
- 対応: Chromeウェブストア／社内配布ポリシーを一切使わず、`edge://extensions`の**開発者モードでの手動インストール（「展開して読み込み」）**とする。実機で開発者モードON操作に警告が出ないことを確認済み
- 対象PCの拡張機能一覧に社内DLP監視ツール「**SS1ADEG(140100_MV3)**」が存在（現在は無効化状態）。将来有効化された場合、本機能（Excelデータの外部送信に類する動作）が検知される可能性があるリスクを認識した上で、ユーザー自己判断・自己責任で進行することに合意済み

### 2.4 方式比較表

| | 断念案Z（Graph API OAuth） | **採用（SharePoint REST API + 拡張機能）** |
|---|---|---|
| 認証方式 | OAuth 2.0（Azure AD同意画面） | なし（ブラウザの既存SharePointログインCookieを利用） |
| IT部門関与 | 必要（実機検証の結果ブロックされた） | **不要**（開発者モード手動インストール） |
| 新規コンポーネント | Azure ADアプリ登録のみ | **ブラウザ拡張機能一式（新規開発）+ サーバー側新規API（方式Q確定により追加）** |
| 動作条件 | どのPC・ブラウザでも動作 | **拡張機能をインストールした特定PC・ブラウザでのみ動作**（今回は「ガントチャート操作PC＝社内PC」という前提が成立するため問題なし） |
| リスク | 管理者承認により実現不可だった | 社内DLP監視ツール有効化時に検知される可能性（ユーザー了承済み） |

## 4. 確定事項（旧: 未確定・要確認事項 → ユーザー回答により確定・2026-08-18）

前回セッションでご相談した2つの論点について、ユーザーより以下の回答をいただき、確定した。

### 4.1 「接続コード」認証方式の実体について → 確定

> 「接続コードという言葉は私の方では定義していません。開発の過程であなたが使い始めたのだと考えています。ですので、『新規トークン発行機能』という対応方針でよいと考えます。」

**確定内容**: 既存の「接続コード」に相当する仕組みは存在しなかったことを前提に、**拡張機能専用の新規トークン発行機能を新規実装する**。ユーザーが`account.html`（アカウント管理画面、実装場所は7.1節で具体化）から自分専用のトークンを発行し、拡張機能の初回設定画面（popup.html）に貼り付けて使う。

### 4.2 拡張機能からガントチャートへのタスク反映方式 → 方式Qに確定

> 「『方式P』にするとタブでプロジェクトを開いておく必要があり、使い勝手が悪いと感じます。そのため、使い勝手を考えて『方式Q』を希望します。」

**確定内容**: **方式Q（サーバー直接送信方式）を採用する**。拡張機能はガントチャート画面が開いているかどうかに関わらず単独で動作し、popup.js（拡張機能ポップアップ）からWebGanttサーバーへ直接HTTPS POSTし、サーバー側で対象プロジェクトの`snapshot`にタスクを追加する。

- 方式Pは不採用として記録に残す（2.1節）
- 方式Q採用に伴う設計上の重要な影響（旧設計書4.2節で提示済みの制約、再掲・確定事項として記載）:
  - 現行WebGanttの「タスクデータをPHP側から直接書き込む経路を持たない」という既存設計方針（`docs/google-calendar-import-design.md` 6節）の**初めての例外**として、サーバー側からDBスナップショットを直接書き換える処理を新規実装する
  - ユーザーが同時にそのプロジェクトのガントチャート画面を開いている場合、**WebSocket経由の同時編集の仕組みの外側で更新されるため、原則としてリロードするまで画面に反映されない**（10.3節で緩和策の検討状況を記載。緩和できない場合でも運用上許容とする前提でユーザーは方式Qを選択済み）
  - 同時に開いている場合の競合（サーバーが書き換えた直後にブラウザ側の未保存の編集で上書きされてしまう等）を考慮した排他制御が必要（10.2節）

### 4.3 新規要望（本改訂版で追加・確定）

方式Qへの確定と合わせて、ユーザーから以下3点の新規要望が提示され、実装対象として確定した。

1. **予定選択のチェックボックスUI**（Googleカレンダー連携の画面C相当）
   > 「アドインでガントチャートで送信する時に、予定表の候補の中から、どの予定をタスクとしてガントチャート側に送るか等も『どのプロジェクトに送るか』の選択の時に、チェックボックスが出て選択できるような挙動をして欲しいです。※イメージはGoogleカレンダーの時等と同じようなイメージ」
   → 拡張機能popup.js内で、プロジェクト選択と合わせて取得済み予定の一覧をチェックボックスで選択できるUIを実装する（6節・8.4節参照。`gantt-collab.html`の`renderScreenC()`のUI・挙動パターンを踏襲）

2. **セル内改行区切りテキストの複数タスク分割**
   > 「エクセルの予定表のマス内に記述された内容として、タスクを改行コードで区切られた感じで タスク1 <改行コード> タスク2 <改行コード> タスク3 となっていた場合は、タスク1、タスク2、タスク3というように3つのタスクにして欲しいです。」
   → Excel解析時、セル値を改行コードで分割し、それぞれを独立したタスクとして扱う（9.2節参照）

3. **同一名称タスクの日またぎ結合**
   > 「まったく同じ名称のタスクが日を跨いでいた場合は、連続するタスクとして認識して欲しい」「実装のリソースが必要そうですが、必要な機能なのでやむなしと考えています。」
   → 同一メンバー・同一タスク名が連続する日付にわたって出現する場合、1つの開始日〜終了日を持つタスクとして結合する（9.3節参照。結合アルゴリズムの提案を含むが、境界条件は実装前に再確認が必要な点あり）

### 4.4 アーキテクチャ方針（本改訂版で追加・確定）

> 「今回追加する機能についてサーバー側として、特殊(汎用性は低い)として、コードを明示的に分けたりするようにして欲しい。※目的としては、いずれこの機能が廃れ、使わなくなった場合に分離削除しやすくしておいて欲しい。」

→ 本機能のサーバー側実装（新規API・新規DBテーブル・新規トークン管理ロジック）を、既存コードから完全に分離した専用ファイル・専用テーブルに収める方針を確定した（11節で詳細を定義）。

## 5. Excelファイルの構造・週ブロック検出ロジック（サンプル実データで検証済み・変更なし）

サンプルファイル`予定表(サンプル).xlsm`（シート名「週間予定表」）を実際に解析した結果、以下の構造を確認した。

### 5.1 シート構造

```
行1:      タイトル「週間予定表」
行4:      日付ヘッダー行（B列〜F列に月〜金の日付、Excelシリアル値／DATE型）
行5:      「全体予定」行（A列に固定文字列「全体予定」、B〜F列が該当日の予定セル）
行6〜18:  メンバー行（A列にメンバー名、B〜F列が該当日の予定セル。今回のサンプルでは12名+区切り）
行19:     空行（週ブロックの区切り）
行20:     次週の日付ヘッダー行
行21:     次週の「全体予定」行
行22〜34: 次週のメンバー行
...（最大4週分繰り返し）
```

- 実データ確認: 行4は`B4=2026-08-17, C4=2026-08-18, D4=2026-08-19, E4=2026-08-20, F4=2026-08-21`（月〜金）、行20は前週（`B20=2026-08-10`〜`F20=2026-08-14`）。**セルの数式は`=B20+7`（現在週）、`=B4+1`のように前週からの相対計算**になっており、値ベース（`data_only=True`で計算済みの値を取得）で読み取れば数式の実装詳細を気にする必要はない
- A列の文字列で「全体予定」行・メンバー行を判定する（A5=`全体予定`固定、A6以降が氏名文字列）
- 日付セルの書式は`mm-dd-yy`だが、値としては通常のExcel日付シリアル値のため、JS側（SheetJS）で日付として正しくパースできることを確認要

### 5.2 週ブロック検出ロジック（提案）

```javascript
// 疑似コード
// 1. A列を上から走査し、「日付らしき値が2つ以上横に並んでいる行」を「週ヘッダー行」として検出
// 2. 週ヘッダー行の直後の行が「全体予定」固定文字列であることを確認（一致しない場合はその週ブロックをスキップしログに警告）
// 3. 「全体予定」行の次から、次の空行 or 次の週ヘッダー行が現れるまでを「メンバー行」として収集
// 4. 上記を最大4週分繰り返す（4週を超えるブロックが見つかっても無視）
```

- `memberCount`（1週あたりのメンバー行数）は固定せず、動的に検出する（サンプルでは12名だが、実際の運用でメンバー数が変動する可能性を考慮）
- 週の並び順は「新しい週が下に来る」か「上に来る」かはサンプルのみでは断定できないため、**両方の日付範囲を見て時系列順に正規化**する（拡張機能側で日付の若い順にソートし直す）

## 6. 機能仕様（確定済み・拡張版）

| # | 項目 | 確定内容 |
|---|---|---|
| 1 | 「全体予定」行の扱い | 1タスクとしてインポート対象に含める（担当者名なしのタスクとして扱う） |
| 2 | メンバー名マッチング | ガントチャートのメンバー一覧に対し、**苗字のみの部分一致**でタスクの担当者(`assignee`)を自動設定する（Excel側は「メンバー01」のようなダミー名だが、実データでは苗字を含むフルネームまたは苗字のみが入る想定） |
| 3 | 空セルの扱い | インポート対象外（該当日・該当メンバーのセルが空なら、その日のタスクは生成しない） |
| 4 | 取得範囲 | 1週間単位、最大4週分（拡張機能のポップアップUIで週を選択、複数週の同時選択も可） |
| 5（新規） | 予定の選択UI | 拡張機能ポップアップで、送信先プロジェクトの選択と合わせて、取得済み予定の一覧をチェックボックスで選択できるようにする（Googleカレンダー連携の画面C相当のUI・挙動。全選択/全解除も用意する） |
| 6（新規） | セル内改行の複数タスク分割 | 1セル内が改行コードで区切られている場合、それぞれを独立したタスクとして生成する |
| 7（新規） | 同一名称タスクの日またぎ結合 | 同一メンバー（または「全体予定」）・同一タスク名の予定が連続する日付にまたがって存在する場合、1つの開始日〜終了日を持つタスクとして結合する |

## 7. 認証・拡張機能起動時のプロジェクト紐付け方式（方式Q確定版）

### 7.1 拡張機能専用トークンの発行

拡張機能はサーバーと直接通信するため（方式Q）、既存のCookieセッション認証とは別に、**拡張機能専用の長期アクセストークン**を新規に用意する。

- **発行場所（提案）**: `account.html`（既存のアカウント管理画面）に新規セクション「拡張機能連携」を追加し、「新規トークンを発行」ボタンでトークン文字列を1回だけ画面表示する（コピーボタン付き。再表示は不可、紛失時は再発行＝旧トークン失効という運用とする）
  - `account.html`は既にAPI呼び出しパターン（`api/auth.php`へのfetch）が確立済みの画面のため、実装コストが低い
- **トークンの実体**: `bin2hex(random_bytes(32))`相当のランダム文字列（既存の`createSession()`と同じ生成方式を踏襲。ただし保存先テーブルは新規・分離: 11節参照）
- **失効・再発行**: 「無効化」ボタンで即座に失効可能。1ユーザーにつき有効なトークンは常に1つのみ（再発行時に旧トークンは自動失効）とし、`office_calendar_tokens`等と同じ`UNIQUE KEY uq_user_id`パターンを踏襲する
- **既存基盤の再利用**: `api/config.php`の`getSessionIdFromCookie()`は既に`Authorization: Bearer xxx`形式をサポート済みだが、`getCurrentUser()`が参照する`sessions`テーブルとは別物のため、**新規トークン専用の検証関数`getUserIdFromExtensionToken()`（仮称）を新規実装**し、`sessions`テーブルには一切触れない形にする（既存の認証フローへの影響をゼロにするため。11節のコード分離方針とも整合）

### 7.2 プロジェクトの指定方法・予定の選択方法（拡張機能ポップアップ内で完結）

方式Qでは「ガントチャート画面を開いている必要がある」という制約がなくなるため、プロジェクトの選択は**拡張機能ポップアップ内のプロジェクト一覧から選ぶ**形になる。

1. 拡張機能の初回設定でトークンを貼り付け済みであることが前提
2. ポップアップを開くと、まず新規API（`GET api/teams_excel_import.php?action=list_projects`）でトークンに紐づくユーザーがアクセス可能なプロジェクト一覧を取得し、ドロップダウン等で表示する
3. ユーザーが対象週（最大4週、チェックボックス）を選択し「取得」ボタンを押す → 拡張機能内でSharePoint REST API経由のExcel取得・解析（5節のロジック）を実行
4. 解析結果（予定一覧）をポップアップ内にチェックボックス付きリストで表示する（**新規要望1**。`renderScreenC()`と同様のUI: 全選択/全解除ボタン、予定ごとのチェックボックス、タスク名・日付・（分かれば）担当者を表示）
5. ユーザーがチェックを入れた予定のみを対象に「送信先プロジェクト」を選択し「インポート実行」ボタンを押す
6. 拡張機能が新規API（`POST api/teams_excel_import.php?action=import_tasks`）へ、選択済みプロジェクトIDと選択済み予定データをまとめて送信する
7. サーバー側で受信データを検証し、対象プロジェクトの`snapshot`にタスクを追加して応答する
8. ポップアップに完了メッセージ（件数）を表示する

この流れにより、**「開いているタブから選ぶ」ではなく、拡張機能単独で「送信先プロジェクトの選択」と「取り込む予定の選択」の両方が完結する**という、ユーザーが希望する使い勝手を実現する。

## 9. データマッピング（新規要望2・3を反映）

### 9.1 フィールドマッピング（基本、変更なし）

| Excelセル | WebGanttタスク |
|---|---|

| 該当セルの文字列（予定内容） | タスク名（9.2節の改行分割適用後は1セル＝1〜N個のタスク名） |
| 空セル | インポート対象外（タスク生成しない） |

### 9.2 セル内改行区切りテキストの複数タスク分割（新規要望2）

1つのExcelセル内に、改行コード（`\n`または`\r\n`。SheetJSでの読み取り結果に応じて両対応する）で区切られた複数行のテキストが含まれる場合、**行ごとに独立したタスクとして分割する**。

```javascript
// 疑似コード（拡張機能popup.js内、Excel解析直後の後処理として実行）
function splitCellIntoTasks(cellValue) {
  if (!cellValue) return [];
  return String(cellValue)
    .split(/\r\n|\r|\n/)      // 改行で分割
    .map(function (s) { return s.trim(); })
    .filter(function (s) { return s.length > 0; }); // 空行除外（要望3の「空セルはインポートしない」の延長）
}
```

- 分割後の各タスクは、**同一の担当者・同一の日付**を持つ別々のタスクとしてそれぞれ生成する（例: 「タスク1\nタスク2\nタスク3」というセルは、同じ日・同じ担当者の3つのタスクになる）
- 空行（改行のみで実質空の行）は生成対象外とする（機能仕様3の「空セルはインポートしない」の考え方を行単位に拡張適用）

### 9.3 同一名称タスクの日またぎ結合（新規要望3）

**確定要望**: 同一メンバー（または「全体予定」）・完全に同一の文字列のタスク名が、**連続する営業日**にまたがって出現する場合、1つの開始日〜終了日を持つタスクとして結合する。

```javascript
//       { assignee, taskName, date } のフラットな配列（9.2節で分割済み）
function mergeConsecutiveSameNameTasks(items) {
  // 1. assignee + taskName の組み合わせでグループ化
  // 2. 各グループ内で date を昇順ソート
  // 3. 日付が「前のタスクの翌営業日」と一致する場合は連続とみなし、
  //    開始日〜終了日の範囲を延長する（1つのタスクにマージ）
```

`import_tasks`実行時のサーバー側処理（疑似コード）:


### 10.3 リアルタイム反映の緩和策（検討事項・実装は任意）

4.2節で確定した通り、方式Qでは原則としてサーバー側の更新はブラウザ側にリアルタイム反映されず、リロードが必要になる。この点について、本セッションの調査で以下の可能性を確認した：

- 既存の`api/notifications.php`に、PHPからNode.js WebSocketサーバー（gantt-ws、ポート3001）へ**内部HTTP POSTで通知をプッシュする前例**（`_pushNotificationToWs()`関数、`http://127.0.0.1:3001/push_notification_batch`）が存在する

- **理論上**、`api/teams_excel_import.php`の`import_tasks`処理の最後に、`_pushNotificationToWs()`と同様のパターンでgantt-wsへ「このプロジェクトにfull_syncをブロードキャストしてほしい」という内部HTTP POSTを送ることができれば、該当プロジェクトを開いている全クライアントの画面がリロードなしで最新化される可能性がある

**ただし**、gantt-ws（`server.js`）の実体は本サンドボックスに存在せず、`full_sync`を外部トリガーで発火させるエンドポイントが現状のgantt-ws側に実装されているかどうかは未確認である。このため:

- 本機能の初版実装では、**この緩和策は実装しない（リロードが必要という前提のまま進める）**
- 将来的にgantt-ws側に対応エンドポイントを追加する余地があるという情報のみ、設計書に記録として残す
- 実装するかどうか、また実装する場合のgantt-ws側の変更要否については、**本番サーバー（`/media/HDD1_DATA/Web/WebGantt/`）側でgantt-ws/server.jsの実装を確認できるユーザー側での追加調査が必要**（本サンドボックスには実体が存在しないため）

## 11. コード分離方針（新規・4.4節の確定要望への対応）

| 種別 | 命名・配置方針 |

| ヘルパー関数 | `api/config.php`など既存の共通ファイルには追加しない。トークン検証関数（`getUserIdFromExtensionToken()`等）も`api/teams_excel_import.php`内にプライベートに定義する（他ファイルからrequireされない前提） |
| 削除時の手順（将来用に事前定義） | (1) `api/teams_excel_import.php`を削除、(2) `DROP TABLE teams_excel_*`、(3) `account.html`内の「拡張機能連携」セクションのHTML/JSブロックを削除、の3ステップで完全撤去できるようにする |

### 11.2 拡張機能側

- 拡張機能自体はWebGanttのリポジトリ本体には含めない、独立したフォルダ（`webgantt-teams-excel-importer/`）として管理する（Gitリポジトリに含めるかは実装時に相談。少なくとも`gantt/`・`api/`・`collab/`配下の既存構造とは完全に独立させる）
- 拡張機能が使わなくなった場合は、`edge://extensions`から削除するだけで完結し、サーバー側に影響を与えない

### 11.3 `account.html`側の追加分

- 新規セクション「拡張機能連携」は、既存のセクションと明確に分離されたHTMLブロック（例: `<section id="teamsExcelExtensionSection">...</section>`）として追加し、削除時にこのブロックごと除去すれば良い状態にする

## 12. セキュリティ・運用上の注意点（必ずユーザーへ明示・更新版）

- 本機能は**IT部門の関与なし**で導入する（2.3節）。将来的に社内DLP監視ツール「SS1ADEG」が有効化された場合、Excelデータの外部（拡張機能内処理）への受け渡し的な動作が検知される可能性がある。導入・継続利用はユーザーの自己判断・自己責任とする
- 拡張機能はChromeウェブストアを経由しない「開発者モード」でのインストールとなるため、**ブラウザの更新やプロファイルのリセット等で拡張機能が無効化・削除される可能性がある**（都度再インストールが必要になる場合がある旨、ユーザーへ事前案内が必要）
- SharePointの認証はブラウザの既存ログインセッションに依存するため、**SharePoint側のセッションが切れている場合は拡張機能側でエラーになる**（この場合はブラウザで一度SharePoint/Teamsにログインし直してから再実行する運用になる）
- **（方式Q確定に伴う追加注意点）** 拡張機能専用トークンは、`Authorization: Bearer`ヘッダーで毎回サーバーに送信される長期有効な認証情報のため、**トークン文字列自体の取り扱いに注意**（拡張機能のstorageから漏洩した場合、そのプロジェクトへのタスク追加権限が第三者に渡るリスクがある）。紛失・流出の疑いがある場合は`account.html`から即座に無効化できる運用とする
- **（方式Q確定に伴う追加注意点）** サーバー側でDBスナップショットを直接更新するため、10.2節で述べた排他制御・競合リスクを踏まえ、**「インポート実行中は該当プロジェクトの画面編集を一時的に控える」運用上の注意喚起**をユーザー向け利用手順に明記する
- 方式Qを採用したため、旧版（方式P想定）で記載していた「サーバー・DBには一切変更が入らない」という記述は撤回する。**本番サーバーへの反映時は、新規APIファイルの配置に加え、新規DBテーブルのマイグレーション（`docs/sql/`配下にDDLを用意し、ユーザー側で`mysql`コマンド実行）が必要になる**（14節参照）
