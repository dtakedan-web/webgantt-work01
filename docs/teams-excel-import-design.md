## 1. 目的・概要

Teams（SharePoint/OneDrive）で共有されている週間予定表Excel（`予定表(サンプン).xlsm`と同一フォーマット）から、メンバーごとの予定を読み取り、WebGanttのタスクとしてインポートする機能を追加する。

**本機能の最大の特徴（Google/Outlookカレンダー連携との違い）**: WebGantt本体（`gantt-collab.html`）やサーバー（PHP API）だけでは完結せず、**ユーザーのブラウザにインストールする新規コンポーネント「ブラウザ拡張機能（Edge/Chrome、Manifest V3）」が必須**となる。これは、Excelファイルの取得に必要な認証（SharePointのブラウザCookie認証）が、WebGanttサーバー側からは技術的に到達不可能な社内ネットワーク内の認証情報であるため。

**対象範囲（本フェーズ）**: Teams OneDriveで共有された`.xlsm`形式の週間予定表のみ。取得範囲は1週間単位で最大4週分。

## 2. 方式検討の経緯（重要・必読）

### 2.1 断念した方式

| 案 | 内容 | 結果 |
|---|---|---|
| 案X | 本番サーバー（`/media/HDD1_DATA/Web/WebGantt/`）から社内LAN経由でExcelにアクセス | **不採用**（サーバー設置環境の制約により社内LANへの経路が無い） |
| 案Y | ユーザーが手動でExcelファイルをアップロード | **ユーザー却下**（「外部連携と趣旨が変わる」、都度手動DL＋アップロードの手間を避けたい） |
| 案Z | Microsoft Graph API + Azure AD OAuth（`Files.Read`スコープ） | **断念確定**。`REDACTED-EMAIL`実機テストで「管理者の承認が必要」ブロック画面を確認。Task B（Googleカレンダー連携時のGraph API検討）・Task C（Outlookカレンダー連携時の`Calendars.Read`検討）と全く同じ`risk-based step-up consent`の壁（`docs/office-calendar-import-design.md` 2.1節参照） |

### 2.2 採用方式: SharePoint REST API（Cookie認証）+ ブラウザ拡張機能

ユーザーから示された重要な制約「**ガントチャートを操作するPCと、会社アカウント(`REDACTED-EMAIL`)を使うPCが同一**」を前提に、以下を実機検証した：

1. ブラウザの開発者コンソールから `fetch(location.origin + "/sites/msteams_b3d137/_api/web/currentuser", {credentials:'include'})` → **`status: 200`**
2. SharePointの`shares` API（`https://suzumond.sharepoint.com/_api/v2.0/shares/{base64エンコードされた共有URL}/driveItem`）を叩き、`@content.downloadUrl`（署名付きダウンロードURL）を取得 → **`status: 200`**
3. 取得した`downloadUrl`から実際にファイルをfetchし、`blob.size`（510,811バイト）・`blob.type`（`application/vnd.ms-excel.sheet.macroenabled.12`）を確認 → **成功**

**結論**: Azure AD OAuth・Graph API・アプリ登録・管理者同意のいずれも一切経由せず、**ブラウザの既存Cookie認証だけでExcelファイルの完全なバイナリを取得できる**ことが実証された。この仕組みをコード化して自動実行するには「ブラウザの中で動作するプログラム」が必要であり、それが実現できるのが**ブラウザ拡張機能**である。

### 2.3 拡張機能の配布・運用方針

- 社内ITポリシー確認の結果、`edge://policy`で`ExtensionInstallForcelist`/`ExtensionSettings`が既にAD経由で運用中であることが判明
- ユーザー方針: **「情報システム部門への確認は難しい。IT部門を回避した形で進めるしかない」**（明言・確定）
- 対応: Chromeウェブストア／社内配布ポリシーを一切使わず、`edge://extensions`の**開発者モードでの手動インストール（「展開して読み込み」）**とする。実機で開発者モードON操作に警告が出ないことを確認済み
- 対象PCの拡張機能一覧に社内DLP監視ツール「**SS1ADEG(140100_MV3)**」が存在（現在は無効化状態）。将来有効化された場合、本機能（Excelデータの外部送信に類する動作）が検知される可能性があるリスクを認識した上で、ユーザー自己判断・自己責任で進行することに合意済み

### 2.4 方式比較表

| | 断念案Z（Graph API OAuth） | **採用（SharePoint REST API + 拡張機能）** |
|---|---|---|
| 認証方式 | OAuth 2.0（Azure AD同意画面） | なし（ブラウザの既存SharePointログインCookieを利用） |
| IT部門関与 | 必要（実機検証の結果ブロックされた） | **不要**（開発者モード手動インストール） |
| 新規コンポーネント | Azure ADアプリ登録のみ | **ブラウザ拡張機能一式（新規開発）** |
| 動作条件 | どのPC・ブラウザでも動作 | **拡張機能をインストールした特定PC・ブラウザでのみ動作**（今回は「ガントチャート操作PC＝社内PC」という前提が成立するため問題なし） |
| リスク | 管理者承認により実現不可だった | 社内DLP監視ツール有効化時に検知される可能性（ユーザー了承済み） |

## 4. 未確定・要確認事項（★実装着手前に必ずユーザー確認が必要）

設計を進める中で、前回セッションまでに合意されていた前提と矛盾する技術的事実が2点判明した。申し訳ないが、実装に入る前にこの2点についてご判断をいただきたい。

### 4.1 「接続コード」認証方式の実体について（要確認）

論点2でご賛同いただいた「選択肢C：接続コードでの初回認証＋ポップアップでのプロジェクト選択」について、本セッションでコードベースを再調査した結果、**WebGanttには「接続コード」に相当する既存の仕組みが実装されていない**ことが判明した。

- `connect_code` / `connection_code` 等のキーワードでコード全体をgrep → ヒットなし
- 「接続者」というキーワードはヒットするが、これは`collab-client.js`の**WebSocketプレゼンス機能**（今誰がプロジェクトに接続中かを表示する`#collab-presence-menu`）を指しており、認証トークンの発行とは別の概念
- `api/config.php` / `api/auth.php`を確認した限り、現状の認証はCookieベースのセッション認証（ログインID/パスワード → `gantt_session`Cookie）のみで、それ以外の「コード」方式の認証は存在しない

**対応方針（提案）**: 既存の「接続コード」を流用するのではなく、**拡張機能専用の新規認証の仕組みを新規設計する**（7節）。これは実質的に「APIトークン発行」機能であり、ユーザーが`account.html`（アカウント管理画面）から自分専用のトークンを1つ発行し、それを拡張機能の初回設定画面に貼り付ける、という流れになる。既存の「接続コード」という言葉のイメージに近い体験（短い文字列を1回貼り付けるだけ）は再現可能。

→ **確認したいこと**: この「新規トークン発行機能」という対応方針でよいか。あるいは「接続コード」について別の既存機能を指していた場合はご教示いただきたい。

### 4.2 拡張機能からガントチャートへのタスク反映方式（新規論点・要確認）

Google/Outlookカレンダー連携（Task B/C）は、`gantt-collab.html`が開かれているブラウザタブの中で完結する機能だったため、既存の**COLLAB-HOOK方式**（`document.dispatchEvent(new CustomEvent('gantt:op', ...))`）でフロントエンドJSのみからタスクを追加し、WebSocket経由で他の同時接続者にも自動同期する、という実装ができた。

しかし**ブラウザ拡張機能は`gantt-collab.html`とは別のJavaScript実行コンテキスト**で動作するため、そのままでは`gantt:op`イベントを発火できない。この制約への対応方式として、以下の2案を提示する。

#### 方式P（タブ連携方式）— サーバー側変更が不要・リアルタイム反映

拡張機能の「Content Script」機能を使い、**今まさに開いているgantt-collab.htmlのタブに対して**、解析済みJSONを渡して`gantt:op`イベントを発火してもらう方式。

```
拡張機能ポップアップでExcel取得・解析
   ↓（chrome.tabs.sendMessage）
gantt-collab.htmlのタブに常駐するContent Script
   ↓（window.postMessage 等でページ本体のJSに橋渡し）
gantt-collab.html側の新規関数 importTeamsExcelEvents(events)
   ↓（Google/Office版と全く同じCOLLAB-HOOKパターン）
document.dispatchEvent(new CustomEvent('gantt:op', {op:'state_sync', subtype:'teams_excel_import', ...}))
```

- **利点**: サーバー側の新規API・新規DBテーブルが一切不要。WebSocket経由の同時編集者へのリアルタイム反映も自動的に機能する（Google/Office版と全く同じ仕組みを流用するだけ）。認証も既存のセッションCookieのまま（拡張機能がサーバーと直接通信しないため、4.1節の「新規トークン」も不要になる）
- **制約**: **取り込み先のプロジェクトのガントチャート画面を、あらかじめ同じブラウザで開いている必要がある**（開いていないと拡張機能側で「対象タブが見つかりません」というエラーになる）。論点2で想定していた「ポップアップでのプロジェクト選択」は、「今開いているタブの一覧から選ぶ」という形に変わる（プロジェクトを開かずに任意のプロジェクトへ送り込む、ということはできない）

#### 方式Q（サーバー直接送信方式）— 論点2の想定に近いが新規サーバー実装が必要

拡張機能からWebGantサーバーへ直接HTTPS POSTし、サーバー側でプロジェクトのタスクデータ（`projects`テーブルの`snapshot`カラム）を直接更新する方式。

```
拡張機能ポップアップでExcel取得・解析
   ↓（fetchでサーバーへPOST、7節のトークン認証）
新規API api/teams_excel_import.php ?action=import_tasks
   ↓（サーバー側でDBのsnapshotを直接読み込み・タスク追加・書き込み）
projects テーブルの snapshot 更新
```

- **利点**: ガントチャート画面を開いていなくても、拡張機能単独でインポートが完結する。論点2でイメージしていた「ポップアップで任意のプロジェクトを選ぶ」という体験に忠実
- **制約（重要）**: 現行のWebGanttは「タスクデータをPHP側から直接書き込む経路」を持たない設計（`docs/google-calendar-import-design.md` 6節で判明した既存の重要な設計方針）。この方式を採用する場合、**既存の設計方針の例外として、初めてサーバー側からDBスナップショットを直接書き換える処理を新規実装する**ことになる。加えて、**ユーザーが同時にそのプロジェクトのガントチャート画面を開いている場合、WebSocket経由の同時編集の仕組みの外側で更新されるため、リアルタイムには反映されない**（ページをリロードするまで画面に表示されない）。同時に開いている場合の競合（サーバーが書き換えた直後にブラウザ側の未保存の編集で上書きされてしまう等）も考慮した排他制御の検討が必要になる

#### 比較表

| | 方式P（タブ連携） | 方式Q（サーバー直接送信） |
|---|---|---|
| サーバー側新規実装 | 不要 | 必要（新規API・認証トークン・DB直接書き込み） |
| 拡張機能とサーバーの通信 | なし（拡張機能↔ブラウザタブ内のみ） | あり（拡張機能→サーバーへHTTPS POST） |
| リアルタイム反映 | ○（既存COLLAB-HOOKで自動） | ×（リロードが必要、競合リスクあり） |
| ガントチャート画面を開いている必要性 | ○必要（対象プロジェクトのタブが開いていること） | ×不要 |
| 4.1節の新規トークンの要否 | 不要 | 必要 |
| 実装の複雑さ・リスク | 低い（既存パターンの延長） | 高い（新しい書き込み経路を作る＝設計方針の例外） |

**提案**: 「ガントチャートを操作するPC＝社内PC」という前提がすでに成立していること、かつ実際の運用が「ボタン押下時に都度実行」（バックグラウンドでの自動実行ではない）であることを踏まえると、**方式P（タブ連携方式）を推奨**する。都度、対象プロジェクトのガントチャート画面を開いた状態で拡張機能を使う運用は、Google/Officeカレンダー連携のUXとも一貫性があり、実装リスクも低い。

→ **確認したいこと**: 方式P・方式Qのどちらで進めるか。方式Pの場合、4.1節の新規トークンは不要になり、その代わりに「プロジェクト選択」は「開いているタブ一覧からの選択」に変わる点をご了承いただけるか。

**本設計書の以降の節は、暫定的に方式P（タブ連携方式）を採用した場合の設計として記述する（ユーザー確認後、必要に応じて方式Qの詳細に差し替える）。**

## 5. Excelファイルの構造・週ブロック検出ロジック（サンプル実データで検証済み）

サンプルファイル`予定表(サンプル).xlsm`（シート名「週間予定表」）を実際に解析した結果、以下の構造を確認した。

### 5.1 シート構造

```
行1:      タイトル「週間予定表」
行4:      日付ヘッダー行（B列〜F列に月〜金の日付、Excelシリアル値／DATE型）
行5:      「全体予定」行（A列に固定文字列「全体予定」、B〜F列が該当日の予定セル）
行6〜18:  メンバー行（A列にメンバー名、B〜F列が該当日の予定セル。今回のサンプルでは12名+区切り）
行19:     空行（週ブロックの区切り）
行20:     次週の日付ヘッダー行
行21:     次週の「全体予定」行
行22〜34: 次週のメンバー行
...（最大4週分繰り返し）
```

- 実データ確認: 行4は`B4=2026-08-17, C4=2026-08-18, D4=2026-08-19, E4=2026-08-20, F4=2026-08-21`（月〜金）、行20は前週（`B20=2026-08-10`〜`F20=2026-08-14`）。**セルの数式は`=B20+7`（現在週）、`=B4+1`のように前週からの相対計算**になっており、値ベース（`data_only=True`で計算済みの値を取得）で読み取れば数式の実装詳細を気にする必要はない
- A列の文字列で「全体予定」行・メンバー行を判定する（A5=`全体予定`固定、A6以降が氏名文字列）
- 日付セルの書式は`mm-dd-yy`だが、値としては通常のExcel日付シリアル値のため、JS側（SheetJS）で日付として正しくパースできることを確認要

### 5.2 週ブロック検出ロジック（提案）

```javascript
// 疑似コード
// 1. A列を上から走査し、「日付らしき値が2つ以上横に並んでいる行」を「週ヘッダー行」として検出
// 2. 週ヘッダー行の直後の行が「全体予定」固定文字列であることを確認（一致しない場合はその週ブロックをスキップしログに警告）
// 3. 「全体予定」行の次から、次の空行 or 次の週ヘッダー行が現れるまでを「メンバー行」として収集
// 4. 上記を最大4週分繰り返す（4週を超えるブロックが見つかっても無視）
```

- `memberCount`（1週あたりのメンバー行数）は固定せず、動的に検出する（サンプルでは12名だが、実際の運用でメンバー数が変動する可能性を考慮）
- 週の並び順は「新しい週が下に来る」か「上に来る」かはサンプルのみでは断定できないため、**両方の日付範囲を見て時系列順に正規化**する（拡張機能側で日付の若い順にソートし直す）

## 7. 認証・拡張機能起動時のプロジェクト紐付け方式（方式P前提）

### 7.1 拡張機能の初回セットアップ（サーバー通信なし）

方式P（タブ連携）を採用する場合、拡張機能はサーバーと直接通信しないため、**Azure AD的な認証もWebGantt独自トークンも不要**。拡張機能が必要とするのは以下の2つの権限のみ：

- `https://suzumond.sharepoint.com/*` へのアクセス権限（Excel取得のため）
- `https://ogma.mydns.jp/*` へのアクセス権限（Content Scriptをgantt-collab.htmlページに注入するため）

### 7.2 プロジェクトの指定方法（「開いているタブから選ぶ」）

1. ユーザーがあらかじめ、WebGanttでインポート先にしたいプロジェクトのガントチャート画面（`gantt-collab.html?project=XXX`）をブラウザで開いておく（複数プロジェクトのタブを同時に開いていてもよい）
2. 拡張機能のツールバーアイコンをクリックしてポップアップを開く
3. ポップアップは`chrome.tabs.query({url: "https://ogma.mydns.jp/WebGantt/gantt/*"})`で、**現在開いている全てのガントチャートタブを列挙**し、プロジェクト名（`document.title`から取得、`gantt-collab.html`は`document.title = projectName`としているため利用可能）の一覧をドロップダウン等で表示する
4. ユーザーが送信先タブ（＝プロジェクト）を選択
5. Excel取得・解析・インポート実行時、選択したタブIDに対して`chrome.tabs.sendMessage`でデータを送る

これにより、論点2で求められていた「プロジェクト選択」の体験は、**接続コードの入力なしに、開いているタブから選ぶ形**で実現できる（4.1節の疑義への実質的な解決策も兼ねる）。

### 7.3 Content Script側の受信処理（新規）

```javascript
// content-script.js（拡張機能側、gantt-collab.htmlページに自動注入）
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type === 'TEAMS_EXCEL_IMPORT') {
    window.postMessage({ source: 'webgantt-teams-excel-ext', events: message.events }, '*');
    sendResponse({ ok: true });
  }
});
```

```javascript
// gantt-collab.html側（新規、既存の外部連携モジュールと同じ<script>ブロック内に追加）
window.addEventListener('message', function (e) {
  if (e.source !== window) return;
  if (!e.data || e.data.source !== 'webgantt-teams-excel-ext') return;
  importTeamsExcelEvents(e.data.events);
});
```

- `importTeamsExcelEvents(events)`関数の内部実装は、`importOfficeCalendarEvents(events)`（`docs/office-calendar-import-design.md` 6.2節）と**ほぼ同一パターン**（`state.rows`/`state.tasks`への一括push→`render()`→COLLAB-HOOK`state_sync`発火、`subtype: 'teams_excel_import'`）とする
- 相違点: 各予定に`assignee`（7.2節のメンバー名マッチング結果）を設定する処理を追加する

## 8. ブラウザ拡張機能の技術設計（Manifest V3）

### 8.1 フォルダ構成（提案）

```
webgantt-teams-excel-importer/
├── manifest.json
├── popup.html
├── popup.js
├── content-script.js
├── lib/
│   └── xlsx.full.min.js   ← SheetJS（CDN不可のためファイルとして同梱）
└── icons/
    ├── icon16.png
    ├── icon48.png
    └── icon128.png
```

### 8.2 manifest.json（権限設計・草案）

```json
{
  "manifest_version": 3,
  "name": "WebGantt Teams Excel Importer",
  "version": "1.0.0",
  "description": "Teams共有Excelの週間予定表をWebGanttに取り込みます",
  "action": { "default_popup": "popup.html" },
  "permissions": ["tabs", "scripting"],
  "host_permissions": [
    "https://suzumond.sharepoint.com/*",
    "https://ogma.mydns.jp/*"
  ],
  "content_scripts": [
    {
      "matches": ["https://ogma.mydns.jp/WebGantt/gantt/*"],
      "js": ["content-script.js"]
    }
  ]
}
```

- `host_permissions`にSharePointドメインを含めることで、拡張機能からのfetchがCookie付きで実行できる（同一ブラウザプロファイル内のログインセッションをそのまま利用）
- 外部CDN（`unpkg.com`等）からのライブラリ読み込みはMV3のCSP制約で不可のため、SheetJSは`lib/`配下にファイルとして同梱する

### 8.3 popup.js の処理フロー（概要）

```
1. chrome.tabs.query() でガントチャートタブ一覧を取得しドロップダウンに表示
2. 週選択UI（チェックボックスで最大4週、日付表示）
3. 「取得」ボタン押下:
   a. fetch(SharePoint currentuser API) で疎通確認（失敗時: 「SharePointにログインしてください」エラー表示）
   b. fetch(shares API) で対象Excelの downloadUrl を取得
   c. fetch(downloadUrl) でExcel実体（ArrayBuffer）を取得
   d. XLSX.read() でパース、5.2節のロジックで週ブロック・予定を抽出
   e. 6節の仕様（全体予定行の扱い・空セル除外・苗字マッチング）を適用しJSON化
4. 「インポート」ボタン押下:
   a. 選択中タブに chrome.tabs.sendMessage で解析済みJSONを送信
   b. 応答を受けて完了メッセージ表示
```

### 8.4 メンバー名マッチング（苗字部分一致）の実装場所

拡張機能はWebGanttのメンバー一覧（プロジェクトメンバーの氏名リスト）を直接知らない（サーバーと通信しない方式Pのため）。そのため、マッチング処理は以下のいずれかで行う：

- **案i（拡張機能側で完結、確定を提案）**: Content Script経由で、対象タブの`gantt-collab.html`が保持している`window.__ganttState`または`getProjectMembers`相当のメンバー一覧をpostMessageで取得し、拡張機能のpopup.js側で苗字マッチングを行ってから`assignee`を確定させた状態でインポート実行する
- 案ii: マッチングをContent Script側（`importTeamsExcelEvents`関数内）で行う。この場合`events`には氏名の生文字列のみを渡し、`assignee`確定処理は`gantt-collab.html`側の新規関数内で行う

→ 実装時、既存の`getProjectMembers`関連コード・プロジェクトメンバー取得の仕組み（`api/projects.php?action=members`）を`gantt-collab.html`側がどう保持しているかを確認した上で、**案ii（gantt-collab.html側でマッチング）を基本方針とする**（拡張機能はメンバー一覧を持たない状態を維持でき、責務がより明確になるため）。

## 10. セキュリティ・運用上の注意点（必ずユーザーへ明示）

- 本機能は**IT部門の関与なし**で導入する（2.3節）。将来的に社内DLP監視ツール「SS1ADEG」が有効化された場合、Excelデータの外部（拡張機能内処理）への受け渡し的な動作が検知される可能性がある。導入・継続利用はユーザーの自己判断・自己責任とする
- 拡張機能はChromeウェブストアを経由しない「開発者モード」でのインストールとなるため、**ブラウザの更新やプロファイルのリセット等で拡張機能が無効化・削除される可能性がある**（都度再インストールが必要になる場合がある旨、ユーザーへ事前案内が必要）
- SharePointの認証はブラウザの既存ログインセッションに依存するため、**SharePoint側のセッションが切れている場合は拡張機能側でエラーになる**（この場合はブラウザで一度SharePoint/Teamsにログインし直してから再実行する運用になる）
- 方式Pを採用する場合、WebGantt側のサーバー・DBには一切変更が入らないため、本番サーバーへの反映作業（`git pull`等）は**拡張機能を使わない他ユーザーには一切影響しない**
